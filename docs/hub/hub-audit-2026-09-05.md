## B1. The hub's URL contract, on one route — proposed, not implemented

One route `/`. Six parameters, all absent-by-default:

| Param | Values | Absent means | Notes |
|---|---|---|---|
| `sport` | `resolveSportParam` (`config.js:89-91`) | ALL SPORTS | **unchanged name, unchanged resolver** |
| `series` | `cup\|oreilly\|truck` | all series | unchanged; only rendered when NASCAR is on the page |
| `day` | `^\d{4}-\d{2}-\d{2}$` | `todayET()` | unchanged format |
| `w` | a week key | the sport's current week | unchanged format; stale keys still fall back (below) |
| `mode` | `day\|week` | **DAY** | new |
| `scope` | `all\|mine` | **ALL** | new |
| `view` | `list\|grid` | **LIST** | new |

Absent-parameter defaults are DAY / ALL / LIST, and **nothing is persisted** (R-B8). A clean
`https://my-sports-xi.vercel.app/` is therefore Today · all sports · all games · list, which is what
the installed app's `start_url` opens (`manifest.js:15`).

**The stale `?w=` behaviour must survive and is cheap to keep.** `weeks/page.js:15-17` records the
intent and `weekChoices` implements it at `108-111`: `all.find(key === pick) || all.find(key ===
currentWeekKey(all, todayET())) || all[0]`. A `?w=nfl-2026-3` under `?sport=cfb` simply does not match
and the page lands on CFB's current week. Keep the chain verbatim.

**WEEK + GRID needs a selected day inside the week. Recommendation: reuse `day`, do not add a
parameter.** Reasons: `day` already exists, already has a format, and already means "the viewing day
being shown"; a second parameter would be a second answer to the same question, and the two would
need a precedence rule the moment someone shared a link. The day strip then simply sets `day`.

**When `day` falls outside `w`.** `w` wins for *which week*, and the strip's active day resolves as
`day if inside the span, else today if inside, else the first day in the span with rows` — the same
shape as `currentWeekKey`'s cascade (`weeks.js:152-168`), and the same recommendation the triage's
C-5 made. It must be a *resolution*, never a redirect: rewriting the URL on load would break
back-navigation, which is the one thing the URL-only model buys.

**Invalid combinations and what each resolves to** — every one resolves, none errors:

| Combination | Resolves to |
|---|---|
| `mode` absent or unrecognised | DAY |
| `scope` / `view` unrecognised | ALL / LIST |
| `w` present, `mode=day` | `w` ignored, kept in the URL |
| `day` present, `mode=week` | `day` is the strip's active day; ignored in WEEK + LIST |
| `w` from another sport | that sport's current week (`weeks/page.js:108-111`) |
| `day` outside `w` in WEEK + GRID | the cascade above |
| `series` with `sport` not NASCAR | control not rendered (`Filters.js:153`); param inert |
| `scope=mine` with an empty favourites file | an honest empty state, never a silent ALL |
| `view=grid` above 699px | R5: the archived render for one sport, an honest line for ALL |

**`WeekSelect` must move to `useSetParam`.** As it stands (`WeekSelect.js:49-53`) it would drop
`mode`, `scope`, `view` and `series` on every week change. This is the single most likely silent
regression in phase 1 and it is two lines.

## B2. Redirects — recommendation: **route-level `redirect()`, not `next.config.mjs`**

| | `redirects()` in `next.config.mjs` | a route-level `redirect()` |
|---|---|---|
| Can forward `?sport=`/`?w=`/`?q=` | only via hand-written `has`/`destination` patterns, one per parameter shape | yes — it reads `searchParams` and composes the target |
| Can translate meaning | no | yes: `/weeks?w=X` → `/?mode=week&w=X`, `/history` → `/?day=<a past day>` |
| Where it lives | build config, invisible to tests that read source | a file under `app/`, readable by `nav.test.mjs`'s own method |
| Cost | 308 at the edge, no function invocation | one server render returning a redirect |

**Recommend route-level.** `/weeks` and `/history` are not renames — they carry meaning that has to
be *translated* into the new parameter model, and `?q=` in particular has nowhere to go under R8, so
the redirect has to decide what to do with it rather than forward it blindly. Keep
`web/app/weeks/page.js` and `web/app/history/page.js` as three-line files that read their params and
`redirect()`. The market-of-one point stands (the only inbound link is the home-screen icon at `/`),
so this is about honesty of translation, not about link rot.

Suggested translations: `/weeks?sport=S&w=W` → `/?mode=week&sport=S&w=W`; `/history?sport=S` →
`/?sport=S&day=<yesterday ET>`; `/history?q=…` → the same, **dropping `q`**, since R8 retires it —
and the build prompt should say so in the redirect's own comment rather than leaving a reader to
wonder where the search went.

# The NOW marker and scroll-to-now (spec §19, triage C-4) — design only

**The marker exists** (§C-1). What follows designs only what does not.

**Where the line is drawn.** `MobileGrid.js:391-399`, at
`left: calc(var(--rail-w) + ${scale.toX(nowMinute)}px)`, full grid height, `z-index: 2` — above the
blocks (auto) and below the sticky rail (3).

**Which clock.** The server request time, read once: `const now = new Date()` at `page.js:154`, turned
into `viewingMinutes(now.toISOString())` at `161`, and **only when `day === today`**. Exactly D1's
discipline — `bandState(rows, now, …)` at `168` takes the same instant. Nothing in the component
reads a clock, so there is no hydration path.

**How it advances between M11's 15-minute refreshes: it does not, and it should not.** The refresh
(`Listing.js:63-67`, `REFRESH_SECONDS = 900` at `config.js:175`) re-requests the route and the server
recomputes the minute. A CSS-only drift is available in principle — animate `left` over 900s — but it
would be **a clock in the render path by another route**: the animation's start would be tied to
hydration time, not to the server's instant, so a tab left open would drift away from the truth the
next refresh snaps it back to. **Recommend: no drift.** A 15-minute granularity on a grid whose
gridlines are 15 minutes apart is honest.

**Initial `scrollLeft` on entry.** Only when `day === today`, i.e. exactly when `nowMinute !== null`
— the component already has the guard. Target `scale.toX(nowMinute) - 0.25 * clientWidth`, clamped to
`[0, scrollWidth - clientWidth]`, so "now" sits a quarter in from the left and the reader can see what
is about to start. It must run **once, after layout, without a clock**: a `useEffect` on the scroller
ref keyed to `nowMinute`, setting `scrollLeft` directly. It must **not** be `scrollIntoView` — that
scrolls ancestors too, and in the viewport-owning grid that would move the page.

**A "jump to now" control** needs: a button in `.mgrid-head` (or beside M8's jump-nav, which already
has the pattern at `MobileGrid.js:336-359`), shown only when `nowMinute !== null`, calling the same
clamped-scroll helper as the entry effect — **one helper, two callers**, or the two will drift.
Optionally hidden until the reader has scrolled away from now, which is a `scroll` listener on the
scroller and cheap.

**The DST edge — confirmed safe, and here is why.** `minutesOfDay` (`gridmodel.js:44-56`) reads the
hour and minute out of `Intl.DateTimeFormat` with `timeZone: 'America/New_York'` and
`hourCycle: 'h23'`. It reads the **ET wall clock**, so the offset comes from the IANA database rather
than from arithmetic. `viewingMinutes` (`62-67`) then applies the 03:00 cutover. **Every block start
and the NOW minute go through the same function**, so on 2026-11-01 both are computed on the same wall
clock and the line cannot land an hour off relative to the blocks. The axis is built from the same
minutes (`axisTicks`, `gridmodel.js:142-155`). The one thing that is *not* handled — and does not need
to be — is that the 01:00–02:00 hour occurs twice that morning; it falls outside the 03:00-cutover
viewing day's rendered span in both passes, so no block and no marker can be placed in the ambiguous
hour.

## G1. Why a sticky axis cannot work in the current scroller — measured, not argued

The brief asked for this statement. It is right, and the measurement makes it precise.

1. `.mgrid-scroll` is `overflow-x: auto; overflow-y: hidden` (`globals.css:1113-1119`). Per CSS
   Overflow, **any** non-`visible` overflow value makes an element a scroll container — `hidden`
   counts. So `.mgrid-scroll` is already the **nearest scrollport** for `.mgrid-axis` inside it.
2. Its vertical scrollable overflow is **zero**: measured on CFB `2026-09-05` at 390,
   `scrollHeight 2960` against `clientHeight 2960`. A sticky box resolves `top` against its nearest
   scrollport, and with nothing to scroll there the constraint is satisfied at the static position
   **forever**.
3. So the page scrolling underneath is irrelevant — the page is not the axis's scrollport.

**Proved on `main` before anything was built:** `position: sticky; top: 0` was applied to
`.mgrid-axis` at runtime and the page scrolled 300px. The axis moved from `top: 2940` to `top: 2640`
— **300px, one for one, zero stickiness.** (`web/qa/tools/sticky-proof.mjs`.)

A fourth reason the brief does not mention: `.mgrid` above the scroller carries `overflow: hidden`
(`globals.css:989-996`), which would **clip** a stuck axis even if the chain were otherwise right.

**Therefore the fix is structural, not a property.** The element that scrolls vertically has to be
the element the axis is sticky inside — which is only possible when the grid is a view of its own.
Interleaved between page sections, it cannot own the viewport. This is the triage's C-3(a), and the
measurement confirms C-3's claim that the hub is what makes §18 buildable.

## G2. What the prototype does

Gated at `page.js:121` (`params?.view === 'grid'`) and `page.js:170` (`<main className="gridview">`).
`Listing` takes `gridViewport` and renders **only** the grid (`Listing.js:125-129`). `MobileGrid`
takes `viewport` and adds `.mgrid-vp` (`MobileGrid.js:118-119, 297`); the axis's rail cell gains
`.mgrid-corner` (`MobileGrid.js:369`). All CSS is appended and scoped.

**Height is layout-driven, and the brief's `calc(100dvh − <measured controls height>)` cannot be
written.** Measured, the chrome above the grid is **350.2px at 360, 361.0px at 390, 375.5px at 430** —
the masthead is a width-proportional SVG, so one literal is wrong at two of three widths by −10.8px
and +14.5px. The viewport is handed down a flex chain instead (`body:has(main.gridview)` → `.shell` →
`.gridview` → `.listing` → `.mgrid-only-vp` → `.mgrid-vp` → `.mgrid-scroll`), scoped with `:has()` so
no other route is touched and no JS width state is introduced.

Stacking, all opaque from `--panel` (rule 16): corner **6** > axis **5** > rail **4** > now **2** >
blocks auto. `touch-action: pan-x pan-y` is unchanged, so one finger scrolls either axis and the pinch
handler still `preventDefault`s the two-finger case itself. **No transform was added anywhere between
the rail and the scroller** (M4 v1.2). The pinch handler is untouched.

**Four traps it hit, each recorded in the stylesheet where it bites:**

1. `min-height: 100dvh` does not constrain a flex chain — flex only distributes *spare* space — so
   nothing shrank and the page kept the scroll. It takes a hard `height`.
2. `.shell` is `max-width: 1100px; margin: 0 auto`. Making `body` a flex column suppresses the
   cross-axis stretch, so it took its max-width: **1100px inside a 390px screen**, the scroller
   inherited **1074px**, and the *page* took the horizontal scroll with the sticky rail on it.
   **The canvas geometry never moved, so the tripwire passed while the layout was wrong** — only
   `clientWidth` said so (1074 against main's 364). `width: 100%` is the whole fix.
3. Body's children are `flex-shrink: 1` by default and the banner — an SVG with no intrinsic
   min-height — **collapsed from 142.2px to 9.1px**.
4. The flat `Listing` branch still rendered the whole day as cards beneath the grid — **9,087px of
   them** — leaving `.mgrid-scroll` 0px tall and handing the scroll straight back to the page.

**The viewport budget, and it is a finding rather than a defect.** With the chrome exactly as `main`
renders it the scroller came out **63px** of an 844px phone. The sticky mechanism was already perfect
at that size; 63px simply is not a grid. Where the 844 goes: banner 142.2 · tab row 45.3 · shell
padding 18 + 64 · DATE row 43.5 · sport block 94 · grid head 60.1 · jump-nav 61 · grid foot 40.2 ·
two global footnotes 46.3 + 29.7 · `.mgrid` margins 14 + 20 = **781, leaving 63**. The prototype gives
back the four that are page chrome for a *scrolling* page (the two footnotes, the shell's bottom
padding, the grid's own footer) → **344px**. It does not touch the DATE row, the sport block, the grid
head or M8's jump-nav. **The masthead plus tab row is still 187.5px, and releasing that is a
ruling** — §F2.

**The three segmented controls — recommendation: `role="radiogroup"` + `role="radio"`/`aria-checked`,
not `aria-pressed` buttons.** The reason is semantics, not syntax: DAY|WEEK, ALL|MINE and LIST|GRID
are each **exactly one of N**, and `aria-pressed` describes N independent toggles that happen to be
adjacent. A screen-reader user hearing "All games, pressed / My teams, not pressed" has to *infer* the
exclusivity; hearing "All games, radio button, 1 of 2, checked" is told it. It also buys arrow-key
navigation as the expected interaction for free. The cost is that a radiogroup takes one tab stop with
arrow keys inside, which differs from the sport tiles (`Filters.js:93-126`, `aria-pressed`, every tile
a tab stop) — **and the sport tiles should stay as they are**, because ALL SPORTS plus eight tiles is
a filter that can be cleared, not a one-of-N choice. Two patterns on one screen is correct here; the
difference between them is real.

**The sticky grid's axis and rail in the accessibility tree.** Both stay in it — the prototype adds
`position: sticky` and `z-index` only, and neither removes an element from the tree. The rail cell
carries the network's mark with a real `alt={row.name}` (`MobileGrid.js:406-408`) or a text label
(`412-417`), so each row is named. The axis labels are plain text spans (`MobileGrid.js:381-385`).
**The one thing to watch:** the NOW marker is `aria-hidden="true"` (`MobileGrid.js:393`), correctly —
it is decorative — but if a jump-to-now control lands, *that* must be announced, and it is the only
thing that would tell a non-visual reader where "now" is.

**Focus order when the grid owns the viewport.** DOM order is head → jump-nav → scroller → blocks,
which is the reading order, so tab order is already right. The risk is the opposite: a scroll
container holding 64 focusable blocks means 64 tab stops before anything after it. In the prototype
there **is** nothing after it, which makes this a non-issue today — but phase 4 should keep it that
way (the grid last in the tab order) rather than adding controls below the scroller.

**Keyboard reach for the ‹ › arrows.** They must be real `<button>`s, not styled spans, and must sit
in the DOM **beside** the picker they step (the §G3 harness places them either side of it). Their
accessible names must say what they step — "Previous day" / "Next day", changing to "Previous week" /
"Next week" with the mode — because "previous" alone is meaningless out of context. They also need a
disabled state at the ends of the loaded range, or they will announce as available and do nothing.
